## [1.1.0] - 2026-11-28

### Added

- A project's public env variables (`NEXT_PUBLIC_`, `VITE_`, `REACT_APP_`, `GATSBY_`, `EXPO_PUBLIC_`, `PUBLIC_`) from its `.env`, `.env.development`, `.env.local` and `.env.development.local` are in `process.env` and `import.meta.env` of every bundle of its code, as its own bundler puts them, so components whose files check their variables when imported render in kitvas. No other name is ever read (ADR 0095).
- Tailwind 3 projects: a kit is learned, built and checked with the project's own Tailwind 3 like a Tailwind 4 one; its tokens map onto theme paths (`theme(colors.primary)`), checked by `kit verify`, and makers, the editor and the code hand-off follow the project's version, prefix and screens (ADR 0094).
- A kit from code in any technology: `kitvas kit new <id> --from code:<folder>` and `/kitvas:learn` read a folder of components as text and write each one again in React, with the project's own names and values. Each component records the project files it came from (`project`), and a hand-off points at the project's own component. `kitvas kit detect` sees such folders as signs: template and partial folders (Handlebars, Laravel, Rails, Hugo, Jekyll, Django) and Angular's component files anywhere in `src/app`.
- Originals: for each example the agent writes the component's own markup as the project draws it (`originals/`), and an example names the page it stands in (`around`) when a rule of that page reaches it (`.article-page .card`); what a component passes into a nested one (a Vue slot, an Angular `ng-content`) takes the passer's scoped styles, as in the app. A picture the app takes from a file or from data (a logo, an avatar) is a plain grey stand-in on both sides, so the kit page shows no broken picture. The new verify step `original` compiles the project's style files (an Angular component's `styles` too), draws the original in kitvas's browser and compares it with the copy in numbers (sizes within half a pixel, every other value exact, hover, focus and pressed looks), then by picture, with whatever floats out of the component's root. Each difference is one finding that names the states and widths it is in.
- Each component of a `code` kit is labelled by how it was checked: compared with the app, compared with the code, or read only with the reason. `kitvas kit verify` prints the counts, and the kit's page shows the label.
- `kitvas kit verify` holds every `var(--kit-…)` in the components of a kit from Figma, a website, images or code to the kit's tokens, with no browser, and names the token's variable when only the spelling differs (`--kit-fontSize-sm` is `--kit-font-size-sm`): a misspelt name left the value unset without a word.
- A kit from code carries the frame the app's pages stand on: its container, columns and gaps become `layout` components (`Container`, `Row`, `Col`, or what the pages repeat) and `space` tokens, whatever the app is written in, and draft makers lay sections out with them instead of their own widths.
- `kitvas studio --kit <id>` opens the studio on that kit's page; `/kitvas:learn` ends there.
- `kitvas kit detect` and `kitvas kit show` name the components whose project files changed (`outdated`); `kitvas kit verify --current <Name>` records one that needed no change. `kitvas kit images <id> --from <folder>` adds pictures to a written kit, and `kit scan` takes a `code` kit.
- `resolve` in kit.json: the folders a project's imports start from (`roots`), the names its bundler puts in place of a folder (`alias`) and the type files nothing imports (`types`), for what the project's build configuration says and its `tsconfig.json` does not. The learner reads the build configuration and writes it. ADR 0092.

### Fixed

- A change made in the editor while the draft was still building from the one before is built too: before, the first build of a new version could mark the newer source as built, and the change never showed.
- A kit learned from a Next app no longer shows its text in a serif: the learner gives the font variables `next/font` sets at run time their family names in the kit's `styles/fonts.css`. The fonts show where they are installed; kitvas copies no fonts. A prop a component only hands on, such as `max` of shadcn's `Progress`, is left out of the kit, and the prop it draws from says how (`value` is a percentage).
- `kitvas kit verify` holds a length the browser works out, such as `calc(var(--radius) - 2px)`, against its token in px, instead of calling it different.
- A kit written from Figma, a website, images or code passes kitvas's element id on to each component's root: the editor can pick the component, and a check names a problem inside it as the kit's own. `kitvas kit verify` holds each component to it in its `render` step.
- A text that is all one inline element, such as a link alone in its block, is measured in that element's font, size, line height and colour, not the block's, also when the markup has spaces or a line break around it: the Figma hand-off draws it as the page does.
- A draft from a kit written from Figma, a website, images or code stands on the source's own page: the kit holds the reset and the `html` and `body` rules in `styles/page.css`, so a draft no longer gets the browser's margin and font.
- A component's own tag in a kit written from code (an Angular `<app-follow-button>`) keeps the look the browser gives it, in line unless the app's styles say otherwise: buttons passed into an author bar stand beside the name, not under it.
- A page's rule goes into a copy from code only when every page that uses the component has it; the agent now looks the pages up in the project's templates, so a button styled by one page (floated right on a profile) no longer floats on every page.
- A text that is hard to read under the pointer or with focus inside a kit component the draft gives no class or style is for review, as the kit's own look, not to fix: a draft on a faithful kit of an app is no longer held to the app's own hover colours. ADR 0096.
- The learn skill's report never says a component renders or looks right when no browser drew it.
- `kitvas kit verify` holds a kit from code to rules W37 and W42 too: a component's own tag drawn as a block where the app leaves it in line is a difference (`display`), and an example that stands in one page while a project file uses the component on another page is a finding.
- A link to a hash router's route (`#/settings`, `#!/settings`) is a link out of the screen, not an anchor to a missing id: `ux/broken-anchor` no longer flags the links of an app with hash routing.
- A console error that React logs with its format string (`%o`, `%s`) and a stack is reported as its message alone, in `kitvas kit verify` and in a draft's check.
- A no-break space (`&nbsp;`) is a letter of the text it stands in, also when it has a node of its own, as before an icon's label: the Figma hand-off and `kitvas kit verify` keep its width.
- A kit of a project that finds its files in its own way no longer fails `kit verify`, a build or a check. Scripts, Sass and the types check now follow one reading of the project's `tsconfig.json` or `jsconfig.json`: `paths`, `baseUrl` as a folder imports start from (also in Sass: `@use 'style/space'`), the configs it extends and references, and the type files its `include` takes in, so a value the project adds to a library's component in a `.d.ts` file is known. ADR 0092.

## [1.0.0] - 2026-11-27

### Added

- Controls in `kitvas check`: every control is put under a real pointer and given keyboard focus at 390 and 1280 px, and its text must keep 4.5:1 there (`a11y/state-contrast`); at 1280 px each button, group of toggles, select and search field is used once, and one that changes nothing on the page is reported (`ux/dead-control`). ADR 0085. Chart bars and skeleton lines are no longer read as placeholder pictures or nested frames, a mapped navigation is not read as moving between states, and text that a sideways scroller cuts off is not measured against the screen edge.
- Shared values: a control in one section can change another. A version declares what a person chooses on the page (a date range, a grouping, a search text) in `src/json/shared.json`; `kitvas layout` writes its type and hands `shared` and `setShared` to every section; the values stay when the studio brings in a new build; `ux/shared-unused` reports a value that no control sets or no section reads; a hand-off to code keeps them as the page's state, set and read by the same sections (ADR 0088). A brief has a Controls part, and `reference/controls.md` holds the rules for makers. ADR 0086.
- Options of a version: one version can hold choices (two or three columns, another kind of card), declared in `src/json/options.json`; the build, the check and the hand-off know them (ADR 0082). `kitvas layout` writes the options type and passes `options` to every section; the check visits each other value at two widths, with the rules `options/no-effect` and `options/unknown`; hand-off takes the default combination. In the editor a style edit goes to all options or to one value alone ("Only Cards: Filled"), written as a block of that value in the section's SCSS; Undo takes the block out again.
- Themes: a kit lists its themes (`tokens.themes`, a token file each; a design system's own switch is named as `attributes` on the body) and a version offers them as the option `theme`; learning takes a system's own themes. The project may add tokens and theme values in `.kitvas/additions/<kit>/`, marked "Added by this project"; compose, rework and craft ask before adding anything (ADR 0083). The mark shows on an added theme in the Options row, on an added token in Properties and in a group of its own on the kit's page; `kitvas kit show` lists the themes and the added tokens, and the code hand-off's brief lists the added tokens a draft uses as tokens to create. `tokens.modes` is gone from the kit contract.
- `CONTRIBUTING.md` (how to report a problem, the setup, what a pull request has to pass) and `CODE_OF_CONDUCT.md` (Contributor Covenant 3.0).
- License: PolyForm Shield 1.0.0 (LICENSE.md) for kitvas, the MIT License (kits/kitvas-ui/LICENSE) for the kitvas UI kit, and LICENSING.md, which says which covers what. kitvas may be used, modified and distributed, including for commercial purposes, provided it is not used to offer competing products or services; the kitvas UI kit may be used, changed and distributed for any purpose; the kitvas name and logo may not be used outside kitvas, and the logo may not be changed.
- `kitvas status` and `kitvas init`, each with `--json`.
- The project's decisions file, `.kitvas/decisions.md`: a short front matter (`kit`, `copy`, `check`) the CLI reads, then dated decisions in five sections that every skill reads and keeps; `kitvas decisions [add | set | replace]` with `--json`, and a `decisions` check in `kitvas doctor` (ADR 0076).
- Kit contract (`kit.json`), DTCG 2025.10 tokens turned into `--kit-*` custom properties, and `kitvas kit list | show | check | component | css`.
- The built-in kit "kitvas UI": tokens, 47 components, 112 icons (the studio's 62 and 50 for product screens: a cart, a bell, a calendar, charts), eight themes and the typeface Figtree; the `/kitvas:kit` skill. The list of its `Select` is drawn in the page from the kit's tokens where the browser can do that, so it opens at its control and at the page's size at any zoom of the canvas (ADR 0087).
- Dependency install into the plugin data folder, from a session hook and from the CLI. The hook's command names only `${CLAUDE_PLUGIN_ROOT}` and reads the data folder from the environment Claude Code gives it (ADR 0011, 0071).
- Drafts with versions in `.kitvas/drafts/`, `layout.md` checked against the kit, generated entry files, and `kitvas draft new | list | show | version`, `kitvas layout`, `kitvas context`.
- `kitvas build`: a draft as a page with the kit's styles, and a stable id on every element written in the draft (`build/json/ids.json`).
- `kitvas check`: build, types and kit rules of a draft as one list of findings with place, element id, message and hint (`build/json/checks.json`).
- Browser checks in `kitvas check`: axe at 390 and 1280 px in every state, blank states, errors and failed files, kit components held to the catalog as they render, and a screenshot per state and width. `kitvas browser` and `kitvas browser install`.
- The studio server: pages and a JSON API on 127.0.0.1 with Host, Origin, Fetch Metadata and token checks, problem details, ETags and a generated OpenAPI document, and a second origin that shows prototypes in a sandbox.
- `kitvas studio [draft]`, `kitvas studio status` and `kitvas studio stop`: the project's studio as a detached process that later commands find again, restarted when the plugin version changes.
- Studio events and jobs: a Server-Sent Events stream with replay after a reconnect, and builds as jobs with time, memory and output limits that can be cancelled.
- Check jobs in the studio, all sharing one browser that the studio starts at the first check and ends when it stops.
- `kitvas inbox`: notes left in the studio reach Claude through a held request.
- Studio pages open only from the one-time link that `kitvas studio` prints.
- Studio pages in the kitvas UI kit's look: a gallery of drafts with live thumbnails and a "Needs attention" filter, and a draft view with width, state and version switches, numbered findings and a next step.
- A live draft view: a state switch moves the prototype's elements to their new places without a reload, the findings are marked on the prototype, the page updates when a build or check ends, and two versions can be compared side by side with what changed, was added or was removed.
- A kit page in the studio: the kit's tokens with swatches, its components with props and examples, its icons as the kit draws them, and its problems. It shows one part at a time, picked on the left (each token group, each component category, the icons); a component folds to its name and what it is for; a search field finds tokens, components and icons by name across all parts.
- Rendered examples on the kit page: each component example in a sandboxed frame, built by the new `kitvas kit build [id]` (as a job when the page opens) and served from the prototype origin (ADR 0029).
- Project kits: `kitvas kit new <id> --from npm:<package>|repo:<folder>`, `kit verify` and `kit use`; kits in `.kitvas/kits/` beside the built-in ones (ADR 0030).
- `/kitvas:learn` learns a whole package: it asks for the core or everything, `kitvas kit exports <id>` lists what the package exports and the kit lacks, several learners write fragments in `<kit>/parts/` that `kitvas kit merge <id>` checks and joins, and the rules point at `reference/kit.schema.json`, the contract as a file. `/kitvas:compose` offers to add a component the kit lacks but the package has (ADR 0081).
- `kitvas kit verify`: schema, imports, types, render and tokens checked against the project's own packages and the browser, with the result in `verify.json` (ADR 0031).
- Packages and React come from the project, so a prototype uses the React of the person's app (ADR 0032).
- Component styles in the bundle: CSS, CSS Modules and Sass imported by components, placed before the draft's sheets (ADR 0033).
- Tailwind v4 kits, compiled with the project's own Tailwind in a child process, and the `ds/tailwind-arbitrary` and `ds/tailwind-unknown` rules (ADR 0034).
- `/kitvas:learn`: a skill and the `learner` agent that write a kit from a package or a folder of the project's components.
- The kit page shows where a kit comes from and whether its last verification still holds.
- An end-to-end test of the stage-1 path through the real CLI and studio, and evals for the three skills.
- `kitvas map [slug]`: the workspace for agents in one answer, drafts or one draft's sections, files and element ids.
- The `/kitvas:compose` skill with the `maker` and `patcher` agents: a draft from a brief, section by section, fixed until its checks pass.
- Quality gate: lint, types, tests with coverage, audit, and architecture, size, English and docs guards.
- Written kits from a Figma file, a website or screenshots: the `tailor` agent writes the components into the kit folder, `kitvas kit scan` reads a website and `kitvas kit crop` cuts the references. `kit verify` gains a sixth step, `look`, that scores each example against its reference. Figma is read only through the person's own MCP server (ADR 0035 to 0038).
- Guidelines with ids and sources, and `kitvas guidelines` for the checklist a skill answers from the screenshots; facts read from the rendered page for the checks (ADR 0043, 0044, 0047).
- `/kitvas:rework` and `/kitvas:craft`: a draft that reworks an existing page or screenshot, and one that sketches a missing component, icon or logo with the `sketcher` agent. `kitvas craft pick | add | export` keep a sketch, put it into the project's additions layer for the kit or write it to a folder; `kitvas kit detect` lists the project's kits and the signs of a design system not learned yet (ADR 0045, 0046).
- A studio address that can be kept, `http://kitvas.localhost:<port>/`, open for 30 days after the first visit, and a studio that stops when nobody uses it (ADR 0040, 0042).
- The editor in the studio: a change made on the canvas is written into the draft's own TSX and SCSS; moving, inserting, deleting and wrapping elements, with element ids kept across edits; canvas tools, press and drag, handles and zoom, Space and drag, with the left or the right button, to pan in Edit and in Preview; every width and state with live checks, waivers, lists and uploads; an undo history kept across a reload; one list item styled apart from the others (ADR 0048 to 0055, 0058 to 0061, 0065 to 0067, 0069, 0070, 0072).
- `/kitvas:edit`: the editor with Claude, through requests, variants, notes, locks, a timeline, suggestions and the reasons for each section (ADR 0056).
- Tools on the canvas: a lens pill (Design, Kit, Checks, Why, Changes) whose pins open what they are about, an ask bar with `/` commands and `Ctrl+K`, a variant pill flipped with `←` and `→`, and an action bar on the selection; the Kit lens reads `GET /api/v1/drafts/{slug}/kit-lens` (ADR 0077).
- "Custom…" in Properties: a colour picker with an eyedropper that previews on the canvas and writes once, and number fields with units, each naming the nearest kit token.
- Checks pane as in the mock: one left edge for headings, cards and lines, cards with two small actions at most (the fix or Ask Claude, then Show on canvas; Ask Claude as an icon beside a fix), and "Accept…" replaced by a Dismiss icon on each card that opens a row of quick reasons ("Fine as it is", "The kit's own look", "False alarm", "Other…") inside the card; a dismissed finding shows its reason and Restore, and leaves the list it was in at once, with the counts. Show on canvas now scrolls the finding's element to the middle of the view and flashes it.
- The live checks of the selected element are one line above Properties (the number of findings, the first one in short words, the element's mark), there for as long as an element is selected and never taller by itself: its cards open on a press and the choice is kept. A finding that comes or goes while you work moves nothing in the pane; with the cards open, the pane scrolls on by what the block grew or shrank. A card names its finding in plain words ("Colour written by hand") with the value, the nearest kit colour and the file and line, and a colour written by hand offers "Use <token>" beside Ask Claude. The card and the "Custom…" editor name the same nearest token.
- The colour picker keeps a drag whole when the panel is drawn again under it, keeps the hue on a grey, comes in once (it no longer plays its entrance after every write), and keeps the cursor on its slider after a write, so the arrow keys go on and Escape still closes it. A long value of your own in a select is cut with an ellipsis instead of widening the pane.
- The change list holds what differs from the last saved version: an undone step leaves it and a redo puts the same line back, so the bar, the Changes tab and the Changes lens count the changes in effect. The mark of a kit component names the kit ("mui component") in Layers and in Properties. In a narrow Layers pane a name ends in an ellipsis before lock and hide, which no longer draw over it and show on hover and for the keyboard only. A click on the canvas beside the cards clears the selection, as a click on empty page does.
- The editor's panes: Layers that fold, versions with the result of their check, Properties in groups with kit values, Changes and Claude with counts on their tabs, and Checks as cards with evidence and the nearest kit token.
- The Insert pane shows each kit component and icon as a picture: `kitvas kit previews` takes them once per kit change, as a studio job (ADR 0075). Uploaded images can be deleted, and an image uploaded twice is kept once.
- Width visits in `kitvas check`: 768 px in every check, and 1024, 1440, 1920 and 2560 px with `--deep`, with rules for button labels on two lines, text in narrow columns, images shown larger than their file and fields that run across a wide page (ADR 0073, 0074).
- The studio's own look, in light and dark, with Cards and Flush layouts and accents (ADR 0057); a start page with the moving logo, the mark as every page's tab icon, Claude's status in every bar, and Guide, Shortcuts and Doctor pages (ADR 0068). The logo is an icon of two kit parts joined by a dovetail, the word `kitvas` and two loose parts (the dot of the "i" and a full stop), in the studio, the brand files and the plugin icon; in the studio its icon and parts follow the accent, and while Claude works the icon's joint moves and the full stop sways, as does the frame's mark of Claude (ADR 0084).
- `kitvas:scout`, an agent that looks facts up on the web for the compose and craft skills and writes one research note (ADR 0062).
- `kitvas doctor`: a report of the setup that holds nothing private, also as a studio page (ADR 0063).
- `kitvas draft delete | restore | purge`, with a trash in `.kitvas/trash/` and a page for a draft in it (ADR 0064).
- A kit page for an id that is not there: a 404 that says so and gives `kitvas kit list`.
- Skill evals for `claude plugin eval` in `evals/`, for the `kitvas`, `kit`, `compose`, `learn`, `craft`, `rework` and `handoff` skills.
- `.claude-plugin/marketplace.json`, so the plugin installs with `claude plugin marketplace add pglejzer/kitvas` and `claude plugin install kitvas@kitvas`.
- Notes are taken from the inbox only by `POST /api/v1/inbox/take` with the studio's Origin; no GET request changes state (ADR 0028).
- Refused requests of the studio and the prototype origin are written to the studio log, without queries, tokens or cookies, at most 20 a minute.
- Stopping a job ends the processes its command started, on Windows, Linux and macOS.
- A job that cannot start keeps the error's own text out of the API; the cause goes to the log.
- `/kitvas:handoff figma <slug>`: a draft goes to the person's own Figma file as editable layers (a page per draft, a frame per width and per section, real text, auto layout, the kit's tokens as variables), from scripts kitvas writes and the skill sends through the person's Figma MCP after a yes (ADR 0078).
- `/kitvas:handoff code <slug>`: a draft goes into the person's project in the project's own technology through the `kitvas:fitter` agent, inside the scope the person gives, then is checked by the project's own scripts and against the draft's shots (ADR 0079).
- `kitvas handoff figma | sent | list | target | brief | changes | compare`, each with `--json`, and the record of a draft's hand-offs in `handoff.json`.
- A `## Handoff` section in `.kitvas/decisions.md`.
- The start page's drafts stand in one group a kit, the project's kit first, each with the kit's name, version and the number of drafts; a draft whose kit is gone from the project keeps its group under the kit's id. A search field in the "Drafts" row filters the cards as you type, by title, slug, kit or kind, and works with the "Needs attention" filter.
