# src/render

Builds the latest version of a draft into `build/html`, `build/js`, `build/css`, `build/json` inside that version.

- The bundler (esbuild), the style pipeline (Sass), the utility CSS (Tailwind) and the disk are ports. Tests of the use case run the real adapters with the fixture kit `tiny`; they are fast enough.
- Element ids come from `domain/sites.ts`: each draft `.tsx` file is compiled alone with `jsxDev`, and the element tree is read from the compiled text. Draft code is never executed in Node. If esbuild changes how it prints dev JSX calls, `readSites` returns `undefined` and the build warns; fix the two patterns there.
- An id is `<file under src/tsx>:<tag>/<tag>` with `.2`, `.3` for later same-tag siblings. Do not put line numbers into ids; positions belong in `build/json/ids.json`.
- The browser part is the JSX dev runtime in the top-level `client/` folder. It only looks ids up in the map compiled into the bundle (`__KITVAS_IDS__`).
- The entry of the bundle is generated (`domain/mount.ts`): the kit's providers around the draft, the state from `?state=`. It never makes the React root itself: it hands the frame runtime (`client/frame/runtime.ts`, alias `kitvas-frame`) a `mount()` that does, and the runtime renders, in the studio switches states with motion, measures elements and draws the marks.
- A bundle may run in a document that an earlier bundle's runtime already runs: the studio's `swap` takes a build into the page in place (ADR 0058, `client/frame/page/swap.ts`). The entry's `startFrame` then only hands the bundle over. So the entry must do nothing else that shows: no root, no listener, no message. The `runtime` it passes is a hash of `runtimeFiles`; a page takes a bundle only when it matches its own.
- Options (ADR 0082): the entry hands `startFrame` the version's options as data (`readOptions`); the runtime reads `opt-*` from the address (`choiceFromQuery`), sets the root's `data-opt-<id>` attributes and passes `render(state, choice)`. The entry parses no address and sets no attribute; a draft without options has `OPTIONS = []`. The studio's prototype origin writes the same attributes on the root of the page it sends (`src/studio/frame/frame-page.ts`), so a theme other than the default shows from the first paint, before the script runs.
- Shared values (ADR 0086): with some, the entry draws the draft through `Held`, a component that keeps them in React state and starts from `holdShared` of the frame runtime, which keeps them on `globalThis` so a swapped-in build starts from what the person chose. A draft without them has no trace of this in its entry.
- Every `client/frame/*.ts` and `client/channel/*.ts` file is listed in `runtimeFiles` (`src/main.ts`), so a change to them rebuilds drafts; a test fails on a missing one.
- A build with errors returns them in the report, leaves the previous output and removes the stamp `build/json/build.json`. Only a layout with problems throws.
- A build is skipped when the stamp's hash matches: draft `src/`, the kit folder, a repo kit's component folder, the runtime files and the files the last utility build read (kept in the stamp as `utility`). Bump `OUTPUT_FORMAT` in `app/build-draft.ts` when the output changes shape.
- The kit catalog (`app/build-catalog.ts`) bundles every example of `kit.json` into one page under `catalogDir` for the studio's kit page; its entry is generated by `domain/catalog-mount.ts` and renders one example per `?example=<key>`. Each example is compiled alone first and left out (`skipped`) when it does not parse. Bump `CATALOG_FORMAT` when its output changes shape.
- The catalog stamp `build/json/catalog.json` is written last and removed by a failed build; `client/frame/page/example.ts` is in `runtimeFiles` like the other frame files. A catalog build writes only `build/`; `verify.json` and `previews/` beside it stay.
- A kit with an icon component gets the icon sheet in its catalog (ADR 0075, `domain/icon-sheet.ts`): one more example under `kitvas-icons`, never in `shown`, its names in the stamp's `icons`. `currentCatalogKey` is the key a build would compare, without building: the studio holds the Insert pane's previews to it.
- Prototypes refer to images as `../img/<file>`, from the page and from the sheet alike.

## Project kits

- Builds call `syncGeneratedEntry` first when `kitWriter` is set, and pass `project` to the bundler. Provider and binding imports that are project paths become absolute paths (`app/project-kit.ts`); everything from kit.json is quoted (`domain/provider-source.ts`).
- The `@kit` alias is `LoadedKit.entry` (ADR 0046): with additions it is the generated entry that also exports them, so never build it from `kit.dir` and `runtime.entry`. The additions folder is part of the build stamp and the Tailwind sources.
- One React: `react` and `react-dom` are aliased to the project's copies when it has React, else to kitvas's. Packages are found up to the workspace root (`packageDirFrom`). A project with a `tsconfig.json` gets `build/json/tsconfig.esbuild.json` (extends it, sets only the JSX options for kitvas's dev runtime) as esbuild's `tsconfig`, so its `paths` still apply.
- A catalog build copies each shown example's `reference` image to `build/img/refs/<key><ext>`: `img/` is a folder the prototype origin serves.
- Styles imported by modules come out of the bundle as CSS: `.css`, `.module.css` as CSS Modules, `.scss` through the Sass plugin (`adapters/scss-plugin.ts`) on the session's one compiler. Fonts and images in them are inlined as data URLs.
- Sheet order in `build/css/index.css`: tokens and themes (`tokenSheet` of the loaded kit), Tailwind, the kit's style files, the bundle's CSS, the draft's sheets.
- Themes (ADR 0083): the entry hands `startFrame` the `attributes` of the kit's themes only when the version has the option `theme` and a theme has some (`themes`); the runtime puts the shown theme's on `<body>` (`client/frame/page/theme-body.ts`), never on the root.
- Tailwind runs in its own process (`adapters/tailwind-worker.ts`, started by `adapters/tailwind-css.ts` with a time, memory and output limit). The compiler comes from the project; kitvas only extracts candidates (`domain/candidates.ts`) and probes the kit's mapped variables, so `--kit-*` always resolves. A Tailwind draft gets `build/json/tailwind.json` with the classes that produced nothing.
