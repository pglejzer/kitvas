# src/checks

Checks the latest version of a draft and writes `build/json/checks.json`. `kitvas check` builds first, so a check always sees the current sources.

- A finding has a rule id `<check>/<name>`, a severity (`fix`: wrong; `review`: a person decides), a place in the draft version, an element id when there is one, and a message with a hint. The shape is `domain/finding.ts`; change it there.
- Rules put their message as a key (`checkRule.<name>`, `checkHint.<name>` in `locales/en.json`); the use case translates. Text from esbuild, Sass and tsc goes through `checkRule.tool` unchanged.
- The `types` check writes `build/json/tsconfig.json`: paths to the kit's entry and to `@types/react` (the project's own when it has them), a project's `tsconfig.json` `paths` with absolute targets (`projectPaths`), and `client/types/assets.d.ts` for style and asset imports. Then it runs tsc from the `typescript` package as a child process. Only errors under `src/` are `fix`. For a project kit, errors outside `src/` are dropped because `kit verify` checks them.
- The `ds` check reads sources, never the page: imports (`domain/code.ts`), plain controls from `ids.json`, and style sheets (`domain/styles.ts`). For a Tailwind kit, also the class strings of the TSX (`domain/tailwind.ts`) against `build/json/tailwind.json`. A size is compared only with tokens of its kind (spacing, radius, font size); a kit without such tokens gets no size findings.
- A new rule (the table of `docs/adr/0020-checks-and-findings.md` now lives in the book, ADR 0043): an entry in `domain/guidelines/`, a rule object `{ id, run }` in `domain/rules/`, four message keys (`checkRule`, `checkHint`, `guideline.<key>.rule` and `.why`), and a test built with the facts builders in `test/checks/rules/facts.ts`. Rules import no Node module. No number outside the book: thresholds come from the entry.
- The book (`domain/guidelines/`): `basis` is `source` only with a fetched https source, else `heuristic`. `fix` only for a sourced threshold or plainly broken output; the rest is `review`. A finding caused by a kit component's own markup is `review` with the `kitInternal` hint. `kitvas guidelines [<id>]` prints the book.
- Page facts (`domain/facts.ts`) are measured in the page, once per visit, then the passes run in this order: `reflow`, `focus`, `deep`, `spacing` (ADR 0044). `deep` precedes `spacing` because the override changes every text's layout. `--deep` adds the extra widths and passes.
- The browser checks (`app/browser-checks.ts`) open `build/html/index.html` from disk in every state at 390 and 1280 px, one browser per run and one context per visit, and write `build/shots/<state>-<width>.png`. Without a browser they are skipped with a note; nothing is downloaded unless the person runs `kitvas browser install`.
- What a visit reports is turned into findings by pure rules: `domain/page.ts` (axe, blank states, errors, console, failed requests) and `domain/usage.ts` (kit components held to the catalog). The JSX runtime in `client/jsx/` records the usage; the bundle's entry puts the kit on `globalThis.__KITVAS_KIT__` so it knows the names.
- Code passed to `page.evaluate` runs in the browser: it uses nothing from its module.
- `kit verify` is `app/verify-kit.ts` with one file per step in `app/verify/` (`schema`, `imports`, `types`, `render`, `tokens`). A step returns issues with a place in kit.json and a message key; nothing is translated here. Only a failed `schema` skips the rest. The answer is also written to `verify.json` in the catalog folder (`domain/kit-verify.ts`).
- `imports` bundles a probe that imports the entry and then every component from its own module: esbuild takes a missing name in a TypeScript re-export for a type and stays silent, so the generated entry alone proves nothing.
- `types` writes `build/json/kit-types.tsx` (`domain/kit-types.ts`): each use on its own lines, with a map from line to claim. Examples that do not parse stay out of it, because tsc reports no type error while a file has a syntax error. Messages in the design system's own files are not reported; only the generated file and the kit's entry are.
- `render` and `tokens` share one catalog build and one browser session, and use `BrowserSession.inspect`. Colours are compared as the browser paints them (`domain/token-compare.ts`), so the kit's hex can be held against oklch or hsl.
- `look` (`app/verify/look.ts`) is the sixth step and runs only for written kits. It captures each example with a `reference` and scores it with the pure `lookScore` (`domain/look-score.ts`): `size`, `colour`, `structure`, the lowest wins, line `LOOK_LINE`. It is advice: a failed `look` makes `valid` false but never blocks drafts. A component with no referenced example is one `lookNoReference`, not a failure.
- `scanKit` and `cropKit` (`app/scan-kit.ts`, `app/crop-kit.ts`) use `BrowserSession.scan` and `crop`. The scan policy (`domain/addresses.ts`) is the only guard against private addresses: every request and redirect goes through it. Facts hold page text only as `{ "pageText": … }` and are checked by `ScanFactsSchema` before they are written (`domain/scan-facts.ts`). Limits live in that file; change them there. Scan, crop and look code that runs in the page uses nothing from its module.
- The studio's shared browser comes in through `PlaywrightOptions.shared`, which `src/main.ts` fills from `SHARED_BROWSER_ENV`. The endpoint is a secret: never log it, print it or put it in a finding.
- Rework (ADR 0045, 0047): `before/` sits next to the version folders (`domain/before.ts`). On a `rework` draft the checks add `ux/protected` and `ux/before-problems` (`domain/rework.ts`) and the `rework` block `{fixed, left}` in `checks.json`. The original's problems are kept uncapped; `MAX_FINDINGS_PER_RULE` limits reports only.
- The `craft` pass (`domain/craft-facts.ts`, `domain/rules/craft.ts`) measures the board's sketches against the kit's icons (`data-craft-sketch`, `data-kit-icon`, `data-craft-tone`); its rule ids are `ui/icon-*` and `ui/logo-*`.
